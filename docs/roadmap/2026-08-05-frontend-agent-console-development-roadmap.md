# Agent Console 前端开发设计规划路线

> 版本日期：2026-08-05
> 项目仓库：`ai-platform-mini`
> 求职目标：Agent 开发工程师 / LLM 应用开发工程师 / AI Platform Engineer
> 文档性质：前端独立开发规划，不代表前端代码已经实现

## 1. 规划目标与范围

### 1.1 当前后端定位

当前项目已经从单纯的 LLM Gateway 演进为一个轻量级 Agent Runtime，后端基础能力包括：

- FastAPI 与 OpenAI-compatible Chat API；
- Ollama/OpenAI Provider 路由、普通响应和 SSE 流式响应；
- API Key 鉴权、限流、Token 配额和 Usage 统计；
- Agent Runtime 的“模型决策 → 工具执行 → 结果回填 → 继续决策或结束”有界循环；
- Agent Run 应用接口：`POST /api/v1/agent/runs`；
- Tool Registry 与 Tool Executor；
- 受限的 `calculator` 工具；
- `knowledge_search` RAG 工具，能够返回知识来源、距离和结构化检索结果；
- MCP foundation，包括工具发现、allowlist、适配器和生命周期健康状态；
- Run Trace Foundation，用于记录 Agent Run、Step、Tool Call、状态、耗时、Token 和错误等执行信息；
- 离线 Evaluation Foundation，包括 30 条本地 golden fixture、确定性 runner 和任务/工具/延迟/Token 指标。

这些能力已经足以支撑一个面向求职作品集的可交互演示，但目前主要通过 API、测试和后端代码体现，面试官不一定能在几分钟内理解 Agent 的执行过程。

### 1.2 前端目标

新增一个独立的 **Agent Console**，目标不是制作一个普通聊天框，而是将后端的 Agent 能力转化为可观察、可操作、可讲解的产品体验：

1. 用户可以输入问题并看到流式回答；
2. 用户可以看到 Agent 是否调用工具、调用了什么工具、工具输入输出和耗时；
3. 用户可以看到 RAG 命中的来源和引用片段；
4. 用户可以看到 Run 状态、步骤数、Token、延迟、Request ID 等运行指标；
5. 工具失败、超时、取消、模型不可用和 SSE 断连都能以清晰的产品状态呈现；
6. 页面在桌面端适合面试演示，在窄屏设备上仍然可用；
7. 前端代码与 FastAPI 后端通过明确的 HTTP/SSE 契约连接，而不是共享内部实现细节。

### 1.3 明确非目标

本规划不要求第一阶段完成以下内容：

- 不把 FastAPI 模板渲染和前端组件强行混在同一个运行时；
- 不重写现有 Chat API 或 Agent Runtime；
- 不在前端实现模型推理、工具执行、RAG 检索或权限判断；
- 不默认把 Agent 的内部思考过程作为“思维链”展示；前端只展示可审计的状态、事件、工具调用和结果摘要；
- 不实现复杂的多租户后台、计费后台、模型训练平台或多 Agent 工作流；
- 不为了视觉效果加入没有后端能力支持的伪造数据。

## 2. React 与 Vue 选型对比

React 和 Vue 都能满足这个项目的前端需求，二者都支持 TypeScript，也都可以使用 Vite 作为独立前端的开发和构建工具。选择标准应以作品集展示、Agent 事件流复杂度、可维护性和求职匹配度为主，而不是把框架选择当成项目本身的卖点。

| 对比维度 | React + TypeScript | Vue 3 + TypeScript |
|---|---|---|
| 组件模型 | JSX 将组件结构与渲染逻辑放在同一模块，适合将消息、事件、工具卡片拆成可组合组件 | 单文件组件将模板、逻辑和样式组织在一起，结构直观，上手成本低 |
| 事件流 UI | 适合用显式状态、Reducer、Query 层和事件归一化模型处理 SSE 增量事件 | Composition API 同样可以完成，响应式模型表达局部状态很自然 |
| TypeScript | 官方文档提供 React + TypeScript 使用方式；生态中类型化组件、数据请求和测试工具较丰富 | Vue 官方提供一等 TypeScript 支持，`create-vue` 可以创建基于 Vite 的 TypeScript 项目 |
| 生态与招聘匹配 | React/TypeScript 在 AI 产品、开发者平台和 Web 应用岗位中出现频率高，迁移到 Next.js 也直接 | Vue 在企业后台和产品开发中成熟，适合已有 Vue 团队或 Vue 生态项目 |
| 可观测界面 | 适合把复杂 Agent Trace 拆成事件 reducer、可复用卡片和面板组合 | 也能实现，但团队需要统一 Composition API、状态和组件边界规范 |
| 学习与演示成本 | 需要明确处理 hooks、状态更新和依赖数组等约束 | 模板语法和响应式 API 对初学者通常更直接 |
| 本项目适配度 | 更适合当前“Agent Console + 事件流 + 面向 AI 工程岗位作品集”的目标 | 技术上可行，但对本项目的求职展示收益相对不如 React 明确 |

### 2.1 选型结论

本项目明确推荐：

> **React + TypeScript + Vite + 独立前端目录**

推荐理由：

1. 当前项目的前端核心难点是 SSE 事件归一化、Agent Trace 展示、工具调用卡片和可扩展信息架构，React 的组件组合和显式状态管理适合这类 UI；
2. React + TypeScript 能够直接展示现代 Web 工程能力，同时保留未来迁移到 Next.js 或接入更复杂 Web 平台的空间；
3. 当前后端已经是 FastAPI，第一阶段没有必要为了前端引入第二套服务端渲染和 API Route；
4. 对求职作品集而言，独立前端能够更清楚地证明“前端通过公开契约消费 Agent API”，而不是把页面和后端模板耦合在一起；
5. React 与 Vue 都是合理选择，推荐 React 不代表 Vue 不好，而是基于本项目的 Agent UI 类型、公开岗位匹配度和后续迁移空间做出的局部决策。

## 3. Vite 独立前端方案

### 3.1 推荐目录和运行边界

建议新增独立的前端目录，例如：

```text
frontend/
  src/
  public/
  package.json
  tsconfig.json
  vite.config.ts
```

这只是目标目录结构，实际创建目录和代码必须由前端子代理按阶段任务完成，并经过 Review 后再进入下一阶段。

推荐运行边界：

```text
浏览器
  ↓
React + TypeScript + Vite Agent Console
  ↓ HTTP / SSE
FastAPI Agent API
  ↓
Agent Runtime / Tool Runtime / RAG / MCP / Run Trace
```

开发环境使用 Vite dev server，通过明确的开发代理或环境变量访问 FastAPI；生产环境可将构建后的静态资源部署到静态托管、反向代理或现有部署入口。前端不应直接导入 Python 模块，也不应读取后端内部数据库。

### 3.2 为什么第一阶段不把前端强耦合进 FastAPI

不建议第一阶段把 React 页面编译产物、模板渲染、FastAPI 路由和前端源码全部绑定在同一套 Python 应用中，原因如下：

- 前后端职责边界更清晰，便于独立测试和部署；
- SSE、鉴权、错误码和响应 Schema 可以通过 HTTP 契约单独验证；
- 前端可以独立使用 Vite 的开发体验、TypeScript 检查和浏览器测试工具；
- 不会为了展示页面改变现有 FastAPI 生产入口；
- 后续如果迁移到 Next.js、静态托管或独立 CDN，不需要重写后端；
- 面试时更容易解释为什么 Agent Runtime 是后端领域层，而 Agent Console 是消费者和可视化层。

这不意味着永远不能将两者部署在同一个域名下。未来可以通过 Nginx、反向代理或静态文件服务统一入口，但部署位置相同不等于源码和职责必须强耦合。

### 3.3 第一阶段不选 Next.js 的原因

Next.js 是成熟的 React 框架，未来如果需要 SSR、复杂路由、登录页面、服务端数据获取或产品化 SEO，可以再评估迁移。但当前目标是一个面向 Agent API 的独立控制台，主要需求是浏览器端交互、SSE 和执行轨迹展示，因此 Vite 更小、更直接，也更适合先验证产品闭环。

选择 Vite 不代表否定 Next.js；它是对当前项目范围的控制，避免在还没有验证 Agent Console 交互价值之前引入不必要的服务端渲染和框架约束。

## 5. Agent Console MVP 设计

### 5.1 MVP 页面

第一阶段只需要一个主控制台和一个轻量的运行历史入口，不做大而全的后台。

#### 页面 A：Agent Console 主页面

核心用途：完成一次 Agent Run，并同时展示回答、事件轨迹和运行指标。

建议布局：

```text
┌──────────────────────────────────────────────────────────────┐
│ 顶部：项目名称 / 新建会话 / 运行状态 / API 配置提示          │
├──────────────────────────────┬───────────────────────────────┤
│ 左侧：对话区                  │ 右侧：Agent Trace              │
│ - 用户消息                    │ - Run 状态                    │
│ - Assistant 流式回答          │ - Step 时间线                 │
│ - 引用标记                    │ - Tool Call 卡片              │
│ - 输入框和发送/停止按钮       │ - RAG 来源                    │
├──────────────────────────────┴───────────────────────────────┤
│ 底部：步骤数 / 延迟 / Token / Request ID / 错误摘要           │
└──────────────────────────────────────────────────────────────┘
```

#### 页面 B：Run History（低优先级）

用于展示已完成或失败的运行摘要：

- Run ID；
- 创建时间；
- 用户输入摘要；
- 状态；
- 步骤数；
- 延迟；
- Token 使用量；
- 点击进入详情。

如果当前后端尚未提供持久化 Run 查询 API，则 MVP 先不实现真实历史列表，可以保留信息架构和空状态说明，避免前端伪造历史数据。

#### 页面 C：Evaluation Overview（后续）

不作为第一阶段 MVP。等后端评测结果有稳定的读取接口后，再展示：

- Case 数量；
- Task Success Rate；
- Tool Selection Accuracy；
- 平均步骤；
- p95 延迟；
- Token 总量与均值；
- 失败 Case 分类。

### 5.2 信息架构

前端状态建议围绕领域对象组织，而不是围绕组件临时变量组织：

```text
App
├── AgentConsolePage
│   ├── ConversationPanel
│   │   ├── MessageList
│   │   ├── AssistantMessage
│   │   ├── CitationMarker
│   │   └── Composer
│   ├── TracePanel
│   │   ├── RunStatus
│   │   ├── StepTimeline
│   │   ├── ToolCallCard
│   │   ├── RetrievalSources
│   │   └── EventDetails
│   └── RunMetricsBar
└── RunHistoryPage（后续）
```

建议的前端领域类型包括：

- `ConversationMessage`：用户和助手消息；
- `AgentRun`：Run ID、状态、模型、创建时间、结束原因；
- `AgentStep`：步骤序号、类型、状态、耗时；
- `ToolCall`：工具名、输入摘要、输出摘要、状态、耗时；
- `RAGReference`：来源名、文档标识、距离、片段摘要；
- `RunMetrics`：步骤、延迟、Prompt Token、Completion Token、总 Token；
- `AgentEvent`：SSE 事件类型和事件载荷。

前端必须把后端事件先归一化为稳定的领域状态，再交给组件渲染。组件不应直接依赖某个 Provider 的原始响应格式。

## 6. 核心交互设计

### 6.1 普通 Agent Run

1. 用户在输入框输入问题；
2. 点击发送后，前端创建本地的 pending message 和 pending run；
3. 发送 Agent Run 请求；
4. 收到 Run ID 后显示运行状态；
5. 订阅可用的 SSE 流或消费流式响应；
6. 增量更新助手回答和 Trace；
7. 收到完成事件后展示最终答案、引用和指标；
8. 用户可以复制答案、展开详情、重新运行或开始新会话。

### 6.2 工具调用

工具调用必须以明确的状态卡片展示，而不是隐藏在回答文本中：

- `pending`：Agent 已选择工具，等待执行；
- `running`：工具正在执行；
- `completed`：工具成功完成，显示安全摘要和耗时；
- `failed`：工具失败，显示面向用户的错误摘要，不泄露内部堆栈或密钥；
- `timed_out`：工具超时，显示可重试或结束的建议；
- `cancelled`：用户停止了 Run，工具执行被取消或后续事件被忽略。

默认只展示可审计信息：工具名、参数摘要、结果摘要、状态、耗时和来源。不要把未经过滤的内部 Prompt、原始异常堆栈或可能包含敏感信息的完整工具输出直接渲染到页面。

### 6.3 RAG 来源

当 Agent 使用 `knowledge_search` 时，右侧 Trace 和助手回答中应能关联来源：

- 来源文档名或文档标识；
- 命中片段摘要；
- 检索距离或排序信息；
- 来源数量；
- 引用是否参与最终回答；
- 无结果时的明确状态。

来源展示必须基于后端返回的数据，不应根据回答文本猜测引用。

### 6.4 停止、取消和重新运行

- 在运行中显示“停止生成”或“取消 Run”；
- 用户取消后，前端立即停止继续渲染增量事件，并等待后端最终状态或显示“取消请求已发送”；
- 取消不能把已生成的部分答案伪装成完整成功；
- 重新运行应生成新的 Run ID，并保留原始运行结果用于对比；
- 页面刷新或网络恢复后，不应自动假设旧的 SSE 连接仍然有效。

## 7. SSE 流式通信设计

### 7.1 当前能力与待确认边界

当前后端已经提供 Chat SSE 流式能力，Agent Run 也已经存在应用接口和 Run Trace 基础。前端开发前必须先核验 Agent Run 是否已有可直接消费的事件流接口，以及当前事件字段是否足够支撑 Trace 展示。

如果 Agent Run 当前只有最终响应、没有公开的事件流接口，前端任务不能用定时轮询或假事件冒充实时 Trace。应新增一个独立的后端契约任务，例如 Agent Event SSE 或等价的事件读取接口，再由前端接入；该后端任务必须单独设计、实现、测试并经过 Review。

### 7.2 前端事件处理原则

前端事件处理器应具备以下行为：

- 根据事件类型更新消息、Run、Step、Tool Call、来源和指标；
- 允许事件重复或乱序时进行基本防护，至少不能重复追加同一事件导致界面错乱；
- 识别完成、失败、取消和连接错误；
- 对未知事件保留可诊断信息，但不阻塞整个 Run；
- 关闭页面或开始新 Run 时清理旧连接；
- 不把 SSE 网络错误等同于 Agent 已成功完成；
- 处理代理层、浏览器和服务端的连接超时边界；
- 对用户可见错误做脱敏和归一化。

### 7.3 SSE 验收场景

至少验证以下场景：

1. 普通回答可以逐步显示；
2. Agent 调用 calculator 时，工具事件和最终回答顺序正确；
3. Agent 调用 knowledge_search 时，来源卡片在回答前或回答过程中出现，并在最终状态保持；
4. 工具失败时，Trace 显示失败，页面不会无限 Loading；
5. 用户停止 Run 后，后续增量不会继续覆盖当前状态；
6. SSE 连接中断时，页面显示可恢复错误，并保留已经收到的内容；
7. Run 完成后，连接被释放，不继续产生重复事件。

## 8. 分阶段开发任务与验收标准

所有前端代码由子代理实现，主代理只做任务拆分、代码 Review、验证和风险反馈。**每个阶段完成后必须暂停，展示变更并等待用户 Review；只有用户批准后才进入下一阶段。**

### 阶段 0：前端契约和 UI 设计基线

**目标**：在写代码前固定页面信息架构、API 字段映射、状态机和视觉方向。

**交付内容**：

- 前端目录和运行边界说明；
- Agent Run、Agent Event、Tool Call、RAG Reference、Run Metrics 的字段映射；
- SSE 事件类型表；
- 主页面线框或静态设计；
- 错误状态和空状态清单；
- React + TypeScript + Vite 技术决策记录。

**验收标准**：

- 不引入生产代码或修改现有后端行为；
- 每个页面状态都能映射到后端已有字段或明确标记为待补充契约；
- 不使用假数据掩盖后端缺失能力；
- 能解释为什么独立前端比 FastAPI 模板耦合更适合当前目标。

**Review 门**：阶段 0 通过用户 Review 后，才开始阶段 1。

### 阶段 1：React + TypeScript + Vite 基础骨架

**目标**：创建可独立启动的前端工程和最小页面壳子。

**交付内容**：

- 独立 `frontend/` 工程；
- TypeScript 严格配置；
- Vite 开发和构建配置；
- 基础路由或页面切换；
- 基础布局、主题、响应式断点；
- 前端 lint、format、typecheck、unit test 的最小脚本；
- README 中的前端启动说明，若用户批准更新 README。

**验收标准**：

- 前端可以独立启动和构建；
- 页面在桌面和窄屏下没有明显溢出；
- 无业务请求时，空状态和加载状态可用；
- 类型检查和基础测试通过；
- 不修改后端生产代码、后端测试代码或现有业务逻辑。

**Review 门**：展示目录、主要组件、配置和页面截图，等待用户批准后进入阶段 2。

### 阶段 2：对话区与普通流式回答

**目标**：完成最小可用的 Agent Console 对话体验。

**交付内容**：

- 消息列表和输入框；
- 发送、禁用、清空、新建会话；
- Agent Run 请求封装；
- SSE 或后端已确认的流式接口接入；
- 增量文本渲染；
- 完成、失败、取消和连接中断状态；
- Request ID 和 Run ID 的可复制展示。

**验收标准**：

- 能使用真实后端完成一次普通 Agent Run；
- 文本增量不会重复或丢失；
- 发送期间按钮状态正确，不能重复提交同一个请求；
- 取消后不会继续追加旧 Run 的事件；
- 网络失败时用户能理解发生了什么，并可重新运行；
- 至少有浏览器级或组件级测试覆盖核心状态转换。

**Review 门**：展示真实后端演示和代码 Review，等待用户批准后进入阶段 3。

### 阶段 3：Agent Trace 与工具调用卡片

**目标**：让面试官能看到 Agent 的执行链路，而不只是最终答案。

**交付内容**：

- Run 状态和 Step 时间线；
- Tool Call 卡片；
- calculator 成功、失败、超时和取消状态；
- 步骤序号、耗时和状态颜色；
- 事件详情展开/收起；
- 过长输入输出的摘要和安全截断。

**验收标准**：

- calculator 场景可以清楚显示“选择工具 → 执行工具 → 返回结果 → 最终回答”；
- 工具输入输出不会破坏页面布局；
- 工具失败不会让整个页面崩溃；
- 同一个工具事件不会重复显示；
- 不渲染内部堆栈、密钥或未经处理的敏感内容；
- Trace 与回答状态保持一致。

**Review 门**：至少演示一个成功工具调用和一个失败工具调用，等待用户批准后进入阶段 4。

### 阶段 4：RAG 来源和可解释回答

**目标**：用真实知识库场景体现 Agent + RAG + 来源追踪能力。

**交付内容**：

- RAG Reference 卡片；
- 来源名称、片段摘要、距离或排序信息；
- 回答中的来源标记或来源列表；
- 无结果、来源缺失和来源过长状态；
- 来源与对应 Tool Call 的关联。

**验收标准**：

- knowledge_search 场景能显示真实后端返回的来源；
- 没有来源时不伪造引用；
- 来源文本被安全截断，页面保持可读；
- 面试官可以从 Trace 追溯到检索结果，再追溯到最终回答；
- 至少覆盖有来源、无来源、检索失败三个状态。

**Review 门**：演示一个知识库问题的完整链路，等待用户批准后进入阶段 5。

### 阶段 5：可访问性、响应式和错误体验收口

**目标**：把演示页面从“能用”提升到“可维护、可交付”。

**交付内容**：

- 键盘可操作的输入、按钮、展开面板和停止操作；
- 合理的焦点移动和焦点可见性；
- 颜色之外的状态表达；
- `aria-live` 或等价机制提示流式回答和错误；
- 低宽度布局；
- Loading、Empty、Error、Retry、Disconnected、Cancelled 状态；
- 长回答、长工具输出和多条 Trace 的性能处理。

**验收标准**：

- 核心操作不依赖鼠标；
- 键盘用户能够发送、停止、展开 Trace 和复制信息；
- 重要状态不只通过颜色表达；
- 320px 左右窄屏不出现关键内容被遮挡；
- 错误信息具体、可操作且不暴露敏感数据；
- 页面在至少一种现代浏览器中完成手工回归。

**Review 门**：提交可访问性和响应式检查结果，等待用户批准后进入阶段 6。

### 阶段 6：作品集打磨与发布准备

**目标**：将 Agent Console 变成面试官可以快速运行、理解和复现的作品。

**交付内容**：

- 前端启动和后端依赖说明；
- 一键演示步骤；
- 架构图或时序图；
- 截图或短 Demo 视频；
- 失败场景截图；
- 前端测试和质量门禁说明；
- 简历项目描述和技术取舍说明。

**验收标准**：

- 新环境可以按照文档启动；
- 面试官在 3—5 分钟内能看到普通回答、工具调用和 RAG 来源；
- README 中的所有前端能力都能在代码或 Demo 中找到证据；
- 不把规划中的能力写成已完成能力；
- 经过用户最终 Review 后，才能提交和推送。

## 9. 技术风险与控制措施

| 风险 | 影响 | 控制措施 |
|---|---|---|
| Agent 没有公开实时事件流 | Trace 不能真实实时展示 | 先核验后端契约；缺失时单独安排后端 SSE 事件任务，不用假事件或轮询伪装 |
| SSE 代理缓冲或连接中断 | 用户看到延迟或半截回答 | 明确事件结束标记、连接清理、断连状态和重试边界；在真实部署环境回归 |
| 后端事件字段变化 | 前端状态错乱 | 建立前端领域类型和适配层，避免组件直接依赖 Provider 原始响应 |
| 工具输出过大或包含敏感内容 | 页面卡顿或信息泄露 | 后端优先截断和脱敏，前端二次限制渲染长度，不展示堆栈和密钥 |
| Agent 运行时间过长 | 用户误以为页面卡死 | 显示步骤、耗时、当前状态、取消操作和最终原因 |
| 多 Provider 响应格式不一致 | 前端适配复杂 | 只消费 FastAPI 暴露的统一 Agent/Chat 契约，不在前端判断 Ollama/OpenAI 原始协议 |
| 浏览器跨域或鉴权配置不清晰 | 本地无法演示 | 通过环境变量和开发代理配置，文档明确 API Base URL 和 API Key 边界 |
| 过早引入复杂 UI 库 | 依赖膨胀、视觉不一致 | 先确定信息架构和基础组件，再按需要引入轻量 UI primitives |
| 只追求视觉而忽略错误状态 | Demo 现场不稳定 | 每个阶段验收都包含失败、取消、超时和断连场景 |

## 10. 暂不做事项

以下事项不是 MVP 失败条件，除非后续出现明确业务或面试收益：

- 不复刻 ChatGPT 或 Claude.ai 的完整界面和内部交互；
- 不声称使用了 ChatGPT/Claude.ai 的内部技术方案；
- 不实现真实多用户账户、团队空间、计费和权限管理后台；
- 不实现复杂 Prompt 管理、版本发布和实验平台；
- 不实现实时协作、多人编辑、语音、图片、文件拖拽和多模态工作台；
- 不实现多 Agent 编排页面，除非后端先有稳定可评测的工作流 API；
- 不实现数据库级评测报表，除非 Evaluation Foundation 暴露稳定读取接口；
- 不为了展示而伪造 MCP Server、RAG 命中或模型输出；
- 不在前端暴露 API Key、管理员密钥或内部服务凭据；
- 不把“显示工具调用”误写成“显示模型完整思维链”。

## 11. 面试 Demo 脚本

### 场景一：普通回答

输入：

> 什么是 RAG？它和普通的 LLM Chat 有什么区别？

讲解重点：

- Agent 可以直接回答不需要外部知识的问题；
- 页面展示 Run 状态和最终回答；
- 不把所有问题都强行交给工具，体现工具选择策略。

### 场景二：计算器工具

输入：

> 如果每天有 1200 个请求，每个请求平均消耗 800 tokens，一个月按 30 天计算，大约需要多少 tokens？

讲解重点：

- Agent 识别这是适合工具处理的计算问题；
- Trace 展示 calculator 的工具输入、执行结果、耗时和最终回答；
- 前端不是只展示聊天气泡，而是展示可审计的 Agent 执行过程。

### 场景三：知识库问答

输入：

> 根据项目知识库，解释 Agent 是如何选择和执行工具的。

讲解重点：

- Agent 调用 knowledge_search；
- 页面显示真实命中的文档来源和片段摘要；
- 面试官可以沿着“检索 → 回填 → 回答”链路理解 RAG；
- 如果没有命中，页面明确显示无来源，而不是伪造引用。

### 场景四：故障处理

演示方式：

- 暂停或关闭模型服务，或触发工具失败测试；
- 展示连接错误、工具失败、取消和重试状态；
- 说明用户可见错误和内部错误日志是分开的；
- 说明 Agent Run 不会因为前端断开就被误标记为成功。

## 12. 简历与作品集展示要点

简历描述必须只写已经完成并能被代码、测试或 Demo 证明的内容。前端 MVP 完成后，可以考虑使用类似以下表述：

> 设计并实现基于 React、TypeScript 和 Vite 的 Agent Console，通过 FastAPI Agent API 和 SSE 展示 Agent Run、工具调用、RAG 来源、取消、失败状态及 Token/延迟指标；将复杂的 Agent 执行链路转化为可审计的事件时间线，并通过响应式和可访问性设计支持面试演示。

如果只有阶段 1 或阶段 2 完成，则应缩小表述，例如：

> 搭建独立 React + TypeScript + Vite Agent Console，完成 FastAPI Agent API 对接、流式回答和基础错误状态。

不要写成以下未经验证的表述：

- “复刻了 ChatGPT/Claude.ai 前端架构”；
- “使用了 ChatGPT/Claude.ai 相同的技术栈和内部架构”；
- “实现了完整思维链可视化”；
- “实现了生产级多租户 Agent 平台”；
- “实现了真实在线评测平台”，如果实际只有离线 Evaluation Foundation。

作品集页面建议包含：

1. 一张整体架构图；
2. 一张普通问答截图；
3. 一张 calculator Tool Trace 截图；
4. 一张 RAG 来源截图；
5. 一张失败或取消状态截图；
6. 一段 3—5 分钟 Demo 视频；
7. 一段“技术取舍与未完成事项”说明。

## 13. 统一完成定义

每个前端阶段结束时必须满足：

1. 代码由子代理实现，主代理完成 Review，不由主代理直接编写前端代码；
2. 只交付阶段目标范围内的变更，不顺手扩展无关功能；
3. 有正常、失败、取消、超时或断连场景的验证；
4. 前端 format、lint、typecheck、unit test 和必要的浏览器测试通过；
5. 不修改后端生产代码、后端测试代码或现有业务逻辑，除非用户明确批准独立的后端契约任务；
6. 变更内容展示给用户进行 Code Review；
7. 用户明确批准后，才进入下一阶段；
8. 每个 Sprint 更新 README、写不超过 5 句话的学习总结，并使用 conventional commit 提交。

## 14. 学习总结

本规划明确了 Agent 项目的前端价值不在于复制一个普通聊天页面，而在于把 Agent 的决策、工具调用、RAG 来源、状态和成本转化为可观察体验。React + TypeScript + Vite 是当前范围内较小、边界清晰且有利于求职展示的选择，独立前端也能避免为了演示而改变稳定的 FastAPI 后端。通过先固定事件契约、信息架构和阶段验收标准，可以降低 SSE、状态同步和错误处理带来的返工。公开岗位信息只能作为技能匹配参考，不能被扩展成对 ChatGPT 或 Claude.ai 内部架构的未经证实描述。
